## 1. Custom rule set (10 rules, all enabled, none with `(severity ignore)`)

| Rule | Constraint | Applies to |
|---|---|---|
| `hiz_outer_only_in2` / `hiz_outer_only_in1` | disallow track on In2 / In1 | `EMG_HIZ` nets |
| `hiz_no_vias` | disallow via | `EMG_HIZ` nets |
| `hiz_leakage` | clearance ≥ 0.40 mm | hi-Z track/via/zone vs any non-GND, non-hi-Z track/via/zone; **exempt only** track-vs-track when both are fully inside the same TLV9064 area |
| `hiz_track_to_foreign_pad` | clearance ≥ 0.40 mm | hi-Z track/via vs any non-GND, non-hi-Z pad; **exempt only** pads of U501/U502/U503 |
| `hiz_pad_to_foreign_track` | clearance ≥ 0.40 mm | hi-Z pad vs foreign track/via; **exempt only** pad of U501/U502/U503 vs a track fully inside that IC's area (vias are not exempt) |
| `spi_to_hiz` / `spi_to_buf` | clearance ≥ 2.0 mm / ≥ 1.0 mm | SPI_FAST vs EMG_HIZ / EMG_BUF |
| `zone_a_no_digital` | disallow track/via | SPI_FAST/CTRL_SLOW inside the ZONE_A rule area |
| `no_via_in_smd_pad` | `physical_hole_clearance` ≥ 0.10 mm, severity error | any via hole vs SMD pad (same net included) |

`no_via_in_smd_pad` was a `hole_clearance` rule in RB-02 and never fired for a same-net via in a pad (KiCad's `hole_clearance`
skips same-net items). It now uses `physical_hole_clearance`, which evaluates regardless of net: this was proven with a synthetic
board (canary below) and is the rule that reported all 17 via-in-pad of run 14 in this session.

Default `.kicad_pro` rules unchanged: min clearance 0.15, min track 0.15, min via 0.50, min hole 0.30, copper-to-edge 0.50,
min connection 0.15; 14 netclasses (13 + Default), 34 patterns, 90 nets classified.

## 2. Narrowing the hi-Z exemption

### 2.1 What was wrong in RB-03

RB-03 added `!A.insideCourtyard('U50x')` style exemptions so that the TLV9064 pin pitch (0.65 mm, gap 0.25 mm) would not flood the
DRC. A courtyard is a 3-4 mm wide box around the whole package; any foreign track routed inside it, including the AFE rail running
beside a hi-Z track, was silently accepted. That is the blanket exemption the owner rejected.

### 2.2 What replaces it

Six named rule areas (no keep-out flags; they only give the DRC engine a "fully enclosed by" test) generated by
`rb03r_escape_areas.py` and carried in the PCB: `HIZ_ESC_U501_L/R`, `HIZ_ESC_U502_L/R`, `HIZ_ESC_U503_L/R` (L and R are the same
rectangle: the union of both pin columns plus 1.5 mm each side and 0.45 mm past the end pins; one rectangle was needed because the
V+ rail runs between the columns). The exemptions are:

1. hi-Z track vs foreign track: both fully inside the **same** area;
2. hi-Z track/via vs a pad of U501/U502/U503 (the pin-pitch case);
3. U50x hi-Z pad vs a foreign **track** fully inside that IC's area (not vias).

Everything else keeps 0.40 mm: all other parts' pads, tracks outside the rectangles, vias anywhere (the router additionally
keeps vias 0.40 mm from every hi-Z pad, TLV9064 included).

### 2.3 Measured effect on the installed board

`drc_without_hiz_exemptions.json` is the same DRC with every exemption removed: **42 clearance instances**, all at the three
TLV9064 packages (U501 and U502 pins; U503 has none): 27 hi-Z-track-to-U50x-pad, 13 U50x-hi-Z-pad-to-track, 2 track-to-track
(AFE_3V0 V+ pin copper beside the +IN A pin at 0.30 mm). With the narrowed rules: **0 violations**.

`escape_area_purity.json` (`rb03r_escape_purity.py`): tracks and vias inside each rectangle: U501 38 / 4, U502 39 / 2, U503 42 / 4;
**non-IC, non-GND nets under the exemption: 0**. A foreign net routed there would show up as a purity failure even though DRC
would be silent.

### 2.4 Status of every exception

| Exception | Count on the installed board | Status |
|---|---|---|
| Hi-Z track vs U50x pad (pin pitch) | 27 | **NARROWED** (physical IC pad geometry, no alternative) |
| U50x hi-Z pad vs adjacent-pin escape track | 13 | **NARROWED** |
| Hi-Z track vs AFE_3V0 (V+ pin) track inside the IC rectangle | 2 | **NARROWED** (0.30 mm; V+ pin next to +IN A) |
| Any exemption outside a TLV9064 rectangle | 0 | none |
| Unresolved | 0 | — |

Why the track-to-track case cannot be removed: pin 4 (V+) is adjacent to pin 3 (+IN A) with 0.65 mm pitch; the rail track must
leave pin 4 within 0.30 mm of the +IN A escape. Moving the rail pin is not possible.

## 3. Verification integrity (fail closed)

### 3.1 The failure RB-03 exposed

KiCad assigns a net to a class through `net_settings.netclass_patterns` in `.kicad_pro`. When pcbnew saves a board inside a
project it rewrites the project file and the classes/patterns disappear; every `A.NetClass == '...'` rule then matches nothing
and `kicad-cli pcb drc` prints a clean report. RB-03's first "clean" DRC was of that kind. In this session it recurred once more
in a smaller form: running `rb03_seed_hiz_rule.py` on the canonical board path made pcbnew rewrite `.kicad_pro` (sha256 and size
changed, 17.5 → 20.0 kB) and create lock files, although the script only loads the board. It was my own mistake, not a rule fault. It was caught by the canonical-hash check, restored from the unmodified scratch copy
(hash `e4119969…`), and the tools were fixed (3.4).

### 3.2 `rb03r_guard.py check` (static, against `tools/baseline/project_baseline.json`)

Fails (exit 1) when: the netclass table differs; the pattern list differs; any of the 10 critical rules is missing; the
`.kicad_dru` hash differs from the reviewed baseline; a rule carries `(severity ignore)`; `.kicad_pro` relaxes the severity of a
geometric rule (clearance, hole_clearance, physical_*, copper_edge, shorting, courtyard, track/via size, ...); a design rule value
differs; the net → class map computed from the schematic netlist differs for any of 90 nets, or a net falls to Default.

### 3.3 `rb03r_guard.py canary` (dynamic)

Builds two synthetic boards from the real board (every footprint parked 400 mm away so KiCad cannot re-net the test items), runs
`kicad-cli pcb drc` with **the project files the real DRC will use**, and requires:

* 11 negative canaries: each critical rule fires (hiz_leakage ×2 incl. a track leaving the IC area, hiz_no_vias, hiz_outer_only
  In1/In2, spi_to_hiz, spi_to_buf, zone_a_no_digital, hiz_pad_to_foreign_track, hiz_track_to_foreign_pad on a non-TLV part,
  no_via_in_smd_pad);
* 3 positive controls: the TLV9064 exemptions stay silent for a track inside the area.

Installed board: 11/11 fired, 3/3 silent (`guard_canary.txt`).

### 3.4 Pipeline: `tools/rb03r_verify.sh <board> <evidence dir> [--fill]`

1. copies the canonical project into a scratch directory (never writes back), installs the candidate board there;
2. DRC with schematic parity, ERC, netlist export, route audit, geometric via audit, RB-02 module-frame checks, Economic/edge audit,
   analog audit;
3. `rb03r_guard.py check` and `canary` on the scratch project; **exit status 1 if either fails**;
4. writes `canonical_project_sha256.txt` so the canonical `.kicad_pro` / `.kicad_dru` can be compared before and after.

Every RB-03R tool that loads a board with pcbnew goes through `rb03r_safe.safe_pcb()`: a path inside `rev-b-xiao/kicad/` is
copied (with its project files) into a temporary directory first. Verified: running the via audit, GND tie audit and purity audit
against the canonical path leaves `.kicad_pro` byte-identical.
Canonical project files after this work: `.kicad_pro` sha256 `e4119969eadf3131…` (as restored at the end of RB-03R; **regenerated in RB-03S** to `69d9d2a1…`, see `REVB_RB03S_CAP_DECOUPLING_REPAIR.md` 8.1);
`.kicad_dru` `21c0e803…`.

## 4. Negative controls

`tools/rb03r_guard_selftest.py` (`guard_selftest.json`): each mutation of a scratch copy of the project must make the guard exit
non-zero; the unmodified copy must pass.

| # | Mutation | Guard |
|---|---|---|
| 0 | none | exit 0 (pass) |
| 1 | all netclasses except Default removed | detected |
| 2 | netclass patterns removed | detected |
| 3 | one pattern re-assigned to Default | detected |
| 4 | `hiz_leakage` rule deleted | detected |
| 5 | `no_via_in_smd_pad` disabled | detected |
| 6 | `clearance` severity set to `ignore` in `.kicad_pro` | detected (added in this task: first version missed it) |
| 7 | an extra rule appended to the `.kicad_dru` | detected (hash) |
| 8 | `.kicad_dru` missing | detected |

Pipeline-level controls (`negative_controls_pipeline.txt`):

* `rb03r_verify.sh` with `RB03R_PROJECT` = copy with netclasses removed: KiCad DRC prints no error; the guard prints `GUARD CHECK:
  FAIL`; the script exits 1.
* Same with the patterns removed: the canary reports "did NOT fire" for 5 rules and exits 1. This is the exact mode that produced
  the false clean DRC in RB-03.
* Note (honest limit): removing only the class *definitions* but keeping the patterns leaves the canary passing (KiCad matches the
  class by name); the static check catches it. Neither check alone is sufficient; both are in the pipeline.

Seeded geometry regression (hi-Z): `rb03_seed_hiz_rule.py` remains as a unit seed; superseded by the 11 + 3 canaries, which are
executed against the project files on every run instead of once.

## 5. Not covered

* DRC does not check the solder-mask web, annulus ring versus JLC's 0.20 mm recommendation, or the 0.10 mm via-to-mask criterion:
