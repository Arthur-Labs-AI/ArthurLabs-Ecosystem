# M04.7B Phase 4B: grounded revision synthesis and independent verification

Status: implemented and verified offline. This is a FRAMEWORK, not a finished or production-ready feature: the real independent verifier is NOT implemented and NOT calibrated, so no automatic revision can pass in a production configuration, and the feature must not be described as production-ready. NOT activated: the stage is injected by tests only, no command or UI reaches it, Automatic Thought Evolution stays OFF by default, and no live provider request was made. Schema stays v8; M04.7A and the previous milestone documents are unchanged.

## 1. Pipeline (where synthesis sits)
```text
Capture (durable)  ->  distillation claims  ->  identity classifier (JEV or injected)  ->  IdentityResolver (pure)
  REVISE only, with the authorized target and relation  ->  synthesis_request()          (server-built, bounded, same project)
  -> RevisionSynthesizer (async)   -> SynthesisDraft  (untrusted)
  -> validate_draft                -> deterministic vetoes, BEFORE any verifier
  -> RevisionVerifier (async, different model family)  -> PASS | VETO | UNAVAILABLE
  -> storage-facing check (draft_problem)  -> Plan::Revise
  -> enabled/consent re-read -> ONE immediate transaction: compare-and-set revision + evidence + decision (+ other claims) -> commit
  -> ChangedKnowledge::revised
```
Code: `src/synthesis/` (traits, request/draft types, validation, OpenAI adapter, authorization, verifier boundary, `SynthesisStage`) and `distillation/evolution.rs` (`Plan::Pending`, `finalize_pending`, `synthesis_request`). The identity resolver, the Phase 3 transaction, the Phase 2 storage and the Phase 4A JEV adapter are reused unchanged. `EvolutionPipeline.synthesis: Option<SynthesisStage>` REPLACES the hand-written test drafter when present; nothing else can supply revision text. Every external call happens between the snapshot and the commit with NO database lock held (a test edits the store from inside a running synthesis).

Any failure routes the claim to a pending claim (`stage_or_fall_back`: quota overflow becomes an unchecked object, never a loss), recording one allow-listed veto name. The capture and the claim are never discarded.

## 2. Synthesis contract
* `RevisionSynthesizer::synthesize(&SynthesisRequest) -> SynthesisDraft | SynthesisFailure`. The request is owned, bounded and server-built: kind, title, the target's CURRENT text, the expected change class (additive, correction, replacement; from the resolver's relation, never from the model), the claim's title, text and exact words, and quotes of the target's ACTIVE evidence read from the stored captures by code points (at most 8, each at most 600 characters; more means the claim stays pending).
* Sources are server-issued ids: `base` (the current text), `s1..sN` (active evidence quotes) and `new` (the claim's exact words). The model cites only those.
* `SynthesisDraft`: `kind`, `revised_body`, `change`, `retained`, `added`, `withdrawn` (each assertion = short text + source id) and the answering `model`. There is no field for an object, revision, capture or span; the structured-output schema and the strict parser (exact key set) have no place for one, and tests assert the schema omits them.
* The synthesizer cannot choose or alter the target, create a revision, or decide identity. The title and kind are the target's; only the body may change.

## 3. Real adapter and model choice
`OpenAiRevisionSynthesizer` uses Arthur's shared `providers::chat` (now also exposing `complete_json_detailed`: answering model and token usage, an additive change that leaves `complete_json` identical) with `gpt-4.1-mini`, the model already used for distillation and relation proposals. It is non-reasoning, so `temperature: 0` with strict JSON-schema output makes it deterministic. The provider-reported model must start with `gpt-4.1-mini`, otherwise `ModelMismatch` (not retried). Bounded input (14,000 characters), bounded output (16,000), 2 attempts for transport and 429/5xx only (an answer that is unwanted is never retried), at most 2 requests in flight, cancel, redacted usage and cost accounting (`SynthesisUsage`, list price constants in the source). It needs the shared OpenAI LLM credential AND its own `Purpose::Synthesis` authorization; nothing is sent otherwise. Fixed system prompt; captures and ideas appear only inside the JSON user message and the prompt states they are data, not instructions.

## 4. Independent verifier
`RevisionVerifier::verify(&VerifyRequest) -> Verdict::{Pass, Veto(reasons), Unavailable(reason)}`. Reasons: unfaithful to previous, unfaithful to claim, evidence not covered, unsupported assertion, removed existing fact, contradiction, qualifier or negation changed, scope changed, certainty increased, unsupported date/quantity/entity, wrong correction behaviour. It can only block: its vocabulary has no way to name an object, alter the draft, create a revision or promote a claim.

Independence is decided on MODEL FAMILY, never on a name. `SynthesisStage::new` refuses a verifier whose family equals the synthesizer's (`StageError::NotIndependent`), and there is no fallback to the synthesizer. **Available providers:** Arthur wires OpenAI (all text work) and TypeSafe JEV (identity classification only, under its own consent). OpenAI synthesis is family `gpt`, so an OpenAI verifier would not be independent. A JEV-backed verifier would be a different family but needs new, unbenchmarked questions, its own verification authorization and its own disclosure. Therefore the REAL verifier is the disabled boundary `UnconfiguredVerifier` (always `Unavailable`, `available() == false`, so the synthesizer is not even called), and the working verifier in tests is an offline fake. **No automatic revision can pass in a production configuration until a real independent verifier exists.** That is the main incomplete piece (section 11).

## 5. Deterministic checks (run first; they only reject)
Model id; non-empty, at most 2,000 characters, no control characters; kind unchanged; change class equals the authorized one; at most 12 assertions of at most 400 characters; every cited source is server-issued; `added` cites only `new`, `retained`/`withdrawn` never cite `new`; an additive change withdraws nothing and a correction or replacement must withdraw something; at least one added assertion; the text really changes; no number and no inner capitalised name that is absent from every input; the existing text's content terms are kept (70% additive, 50% correction, 40% replacement); at least one term the note brings appears in the result; growth limited to the note's length plus 160 characters; negation count within bounds, and an additive note's "not" may not be dropped. Each veto maps to an audit name (`invalid_draft`, `draft_bad_reference`, `draft_unsupported_fact`, `draft_omits_fact`, `draft_scope_change`). These establish well-formedness and grounding, NOT semantic truth, and the thresholds are conservative heuristics (a false veto only sends the claim to a person), not calibrated constants.

## 6. Evidence and provenance
A synthesized revision has `origin = system` and NO direct span. Evidence rows are written from the claim's own validated span (Phase 2), never from anything a model returned; the model's text is not stored as an interpretation label. `asserts`, `corrects`, `replaces` map from the change class. A correction names the earlier evidence it withdraws only when exactly one stored evidence row is provably the source of the withdrawn assertion; a withdrawn assertion that rests on the original span (which has no evidence row) cannot be named, so all inherited evidence is demoted to historical, which `evidence_support` reports (`inherited_demoted`). Active, historical and withdrawn evidence stay separate; no sentence-level attribution is produced; when what supports the current text is unknown it stays `Unknown` (tested with an automatic revision that has no evidence).

## 7. Atomic commit and races
Unchanged from Phase 3: one immediate transaction, compare-and-set against the exact base revision, per-claim savepoint, rollback of the whole capture on an unexpected write failure. A user edit, a competing automatic revision, a move or an archive during synthesis or verification makes the compare-and-set fail; the claim becomes a pending claim (`stale_target`) and no evidence exists for the uncommitted revision. Duplicate processing reports `fresh = false`, calls the models once and emits no second `revised` event. Events are built only from a committed outcome.

## 8. Consent, authorization and activation
Four separate permissions, none implying another: TypeSafe identity consent (Phase 4A), synthesis authorization (`Purpose::Synthesis`, this phase), verification authorization (`Purpose::Verification`) and the automatic-revision switch (`EvolutionSettings`). `ProviderAuthorization` is a per-provider, per-purpose, disclosure-versioned, default-OFF, durable record; a missing, damaged, foreign or older record means not authorized; nothing migrates. The enabled/consent state is re-read before synthesis, after it, after verification and inside the commit; revocation in flight discards the result (`evolution_withdrawn`). The stage checks both authorizations before any request. No ON switch and no command exist. Phase 5 contract: a user-facing flow must show, per provider, what is sent (the claim's exact words, the target's current text and quotes of its evidence) and write the matching authorization record only on an explicit choice.

## 9. Failure handling
Synthesis failure of any kind, unavailable verifier, a veto, a missing authorization, an exhausted per-capture budget (4 syntheses and 4 verifications by default), a request that cannot be built (too much evidence, a quote that does not resolve) or a changed world all leave the claim pending with a named veto. A synthesis timeout is a transport failure of the adapter (bounded retry, then `synthesis_unavailable`). Provider payloads, prompts and keys are never logged; `Debug` and errors carry fixed codes.

## 10. Offline verification
49 new synthesis tests (45 behavioural, 4 architecture), all through fakes or a localhost fixture, covering: the headline mobile to mobile and desktop revision with provenance from both captures; a second refinement quoting both earlier sources; explicit correction (historical evidence kept) and correction of an earlier automatic assertion (exactly that evidence withdrawn); decision replacement; reframing, unrelated idea, ambiguous referent and contradictory claims; unsupported fact, omitted fact, hallucinated reference, wrong provenance, oversized revision, model mismatch; verifier PASS, every VETO reason, unavailable and unconfigured; missing authorizations; synthesis failures; consent revoked and Evolution switched off in flight; user edit and competing revision during generation; two racing captures; duplicate processing; rollback and restart; Evolution OFF; Automatic Connections OFF; Bulgarian, mixed-language and emoji offsets; prompt injection; unknown evidence attribution; the OpenAI adapter against a localhost server (request shape, parsing, retries, cancel, timeout, no key without authorization); budgets; architecture tests (no storage/graph/command imports, nothing shipped constructs it, the draft vocabulary has no ids or spans, the production endpoint is reachable only through the production constructor). The full suite and Android results are in the review report.

## 11. Known limitations and incomplete functionality
* **No real independent verifier** (section 4). Until one exists the feature cannot make an automatic revision in a production configuration.
* Deterministic checks are lexical heuristics; they miss meaning-level errors (a plausible but wrong sentence made of the right words). Only the verifier can address those.
* Multi-source withdrawal cannot name more than one evidence row (storage supports one target per row), so it falls back to demoting all inherited evidence.
* The candidate shortlist is lexical (Phase 3), so a paraphrase with no shared word never reaches synthesis (the safe default).
* Accuracy on Bulgarian and mixed text is only exercised with scripted drafts; real-model quality is unmeasured.

## 12. Phase 4C evaluation requirements
Before activation: a human-adjudicated corpus (Bulgarian, English, mixed; additive, correction, replacement, reframing, same-topic distinct, ambiguous, multi-source) run through the real pipeline; measured rates of false revision (target: zero in the undisputed hard negatives with a confidence bound, as in the Phase 0 gates), omitted facts, unsupported facts, wrong correction behaviour, verifier veto precision/recall, and the cost per revision; calibration of the deterministic thresholds on real drafts; evaluation of at least one real independent verifier, separate from the synthesizer's family; a repeat of the JEV benchmark on the exact production request shape.

## 13. Production activation blockers
A real independent verifier with its authorization and disclosure; Phase 4C results; the Phase 5 consent, authorization and review UI and a native credential command; the TypeSafe questions in `m047b-phase4a-jev-adapter.md` section 3D; a data-protection review before any public release; and the Android 16 KB-page APK check (native test binaries need `-C link-arg=-Wl,-z,max-page-size=16384`; this phase changes no linker configuration).

## 14. Review invariants (checked against the code and tests)
1. The synthesizer cannot choose an object, revision, capture or span: the draft type, schema and strict parser have no field for one (tests); the target comes from the resolver and the evidence span from the claim.
2. Draft text and every source reference are validated deterministically before the verifier is asked, and again by the storage-facing check and the Phase 2 triggers at commit.
3. The verifier's vocabulary is PASS, VETO or UNAVAILABLE and nothing else.
4. UNAVAILABLE, an unconfigured verifier, or no verification authorization always keeps the claim pending (tested for every reason).
5. Independence is by model family; same-family pairings are refused at construction.
6. Synthesis and verification run between the snapshot and the commit, outside every SQLite transaction (a test writes to the store from inside a running synthesis and from inside a running verifier).
7. The compare-and-set against the exact base revision rejects a user edit or a newer revision (tested for both).
8. Permission is re-read: before synthesis; after synthesis (enabled, TypeSafe consent AND both provider authorizations); after verification (same); and inside the commit transaction immediately before a revision is written (`EvolutionPipeline::allowed`, which includes the synthesis and verification authorizations). A revocation or cancel at any of those points leaves the claim pending (`evolution_withdrawn`, or `synthesis_unavailable` for an adapter cancel).
9. Failure keeps the claim as a pending claim (or an unchecked object at quota) and never touches the capture.
10. Graph events are built from a committed outcome only; a repeated call emits no second `revised` event.
11. Evolution is OFF by default; the injector is `#[cfg(test)]`; architecture tests assert nothing shipped mentions the stage, adapter, authorization or verifier boundary.
12. `distill_capture` still returns the objects NEW claims created; `ArthurClient` is unchanged; the OFF path is the old `record_distillation`.
13. No logging exists in these modules; `Debug` and errors print fixed codes; the adapter's request goes only to the transport, and tests assert the key and capture text are absent from `Debug` and error output.
Test accounting: the Phase 4B filter `synthesis::` also matches 8 EXISTING Recall tests (`recall::synthesis::tests::*`), so "55 passed" meant 47 new tests plus 8 older ones. The full suite rose from 741 to 788 (+47); with the two permission tests added in the final review it is 790.
