
ARTHUR
PHASE 2 — ISOLATED MEMORY + RAG
DeepSeek V4 Flash Implementation Specification
Version 1.0  •  August 2026
PURPOSEThis document is the implementation contract for ARTHUR Phase 2. Phase 2 gives ARTHUR persistent long-term memory and retrieval while enforcing hard separation between Personal and Business domains. DeepSeek remains the remote reasoning model; memory storage, retrieval, indexing, filtering, provenance, and secret controls remain local.

1. Phase 2 Goal
Extend the hardened Phase 1 ARTHUR Core with persistent, mode-isolated long-term memory and a local RAG pipeline. A Personal turn may search and write only Personal memory. A Business turn may search and write only Business memory. The isolation boundary must be enforced by local code and separate stores—not by prompts, model cooperation, or client-supplied namespaces.
Phase 2 must preserve all Phase 1 architectural boundaries: ConversationService remains provider-independent; DeepSeek remains behind ModelGateway; the AI Harness remains behind HarnessAdapter; tool execution remains guarded; session mode remains server-owned.
PHASE 2 NORTH STARIf a bug in the LLM, a malicious prompt, a bad tool result, or a client request tries to cross Personal/Business memory boundaries, the system must fail closed before retrieval or persistence occurs.
2. Entry Gate / Assumptions
Phase 1 build, typecheck, tests, and security regressions pass.
Phase 1 request idempotency and approval state machines are hardened.
Phase 1 mode history partitioning is already fixed or Phase 2 must preserve/finalize that invariant.
Phase 1 secret sanitization boundary is available and must be reused.
DeepSeek V4 Flash remains the configured reasoning provider through ModelGateway.
No Phase 2 component may bypass the Phase 1 tool or model boundaries.
3. Non-Goals — Do Not Implement Yet
Voice, wake word, STT, TTS, audio streaming, or barge-in.
Phone client, node discovery, remote PC/laptop selection, or distributed failover.
AgencyOS, Cost Intelligence, AI Hoster, CRM, billing, or client acquisition logic.
Knowledge-graph UI, Obsidian-style graph visualization, or complex graph databases.
Training/fine-tuning the LLM on memories.
Massive enterprise-scale vector infrastructure.
PDF OCR, image understanding, email/calendar ingestion, or cloud-drive connectors.
Autonomous memory deletion or irreversible summarization without traceability.
Automatic cross-domain sharing between Personal and Business.
4. Architectural Invariants
Invariant
Required behavior
Two memory domains
Personal and Business use separate physical/logical stores, indexes, and store handles.
Server-owned routing
MemoryGateway selects the domain from trusted SessionContext/ArthurMode. Client and LLM cannot choose arbitrary memory stores.
No cross-domain fallback
If the active store fails, ARTHUR must not query the other store as fallback.
Local retrieval
Embedding/index lookup, filtering, hybrid search, reranking, provenance, and memory writes run locally.
Minimal DeepSeek context
Only selected, sanitized retrieved snippets are added to the DeepSeek request.
Source of truth
RAG context is evidence/context, not an authoritative database replacement.
Provenance
Every memory item records source, timestamps, type, confidence, domain, and supersession metadata.
Deletion
A user-visible memory can be removed from structured rows, FTS index, vector index, and future retrieval.
Idempotent ingestion
Replaying the same memory/document ingestion request cannot silently create duplicates.
Prompt injection resistance
Retrieved content is marked as untrusted data and cannot redefine system/tool policies.
Mode-safe context
Personal turns receive only Personal memories; Business turns receive only Business memories.
Replaceable embeddings
Conversation code depends on EmbeddingGateway/VectorStore interfaces, not one embedding model.

12. Local Embedding Layer
Embeddings should remain local in Phase 2 so raw memory does not need to be sent to another external provider. Implement a provider-agnostic EmbeddingGateway with a small multilingual local embedding provider and a deterministic fake provider for tests.
interface EmbeddingProvider {  id(): string  dimensions(): number  embed(texts: string[]): Promise<number[][]>}interface EmbeddingGateway {  embed(texts: string[]): Promise<EmbeddingBatch>}
Model/provider name is configuration, not hard-coded in memory logic.
Store embedding model ID/version on every item/chunk.
If embedding model changes, do not mix vectors silently; mark/reindex explicitly.
Batch embeddings where possible.
Enforce input-size limits before embedding.
Never send secrets that were sanitized out of the canonical memory text.
13. Vector Store Strategy
Phase 2 does not require a dedicated vector database. Store embeddings persistently in each memory SQLite database and expose vector search behind a `VectorStore` interface. A linear/local cosine search is acceptable for the expected Phase 2 dataset if bounded and tested. The interface must allow replacement by pgvector or another vector engine later.
interface VectorStore {  upsert(chunks: EmbeddedChunk[]): Promise<void>  search(queryVector: number[], filters: RetrievalFilter, limit: number): Promise<VectorHit[]>  deleteByMemoryId(memoryId: string): Promise<void>}
14. Keyword / FTS Retrieval
Create an FTS index per memory database for exact names, phrases, IDs, and terms that embeddings may miss. FTS and vector retrieval are combined rather than choosing one.
Only ACTIVE and non-expired memories are eligible.
Project/entity filters are applied before ranking when present.
Deleted/superseded records must never appear.
FTS query generation must be escaped/validated; user text is not inserted as raw SQL.
Result size is bounded.

16. Context Budgeting
Do not dump every retrieved memory into DeepSeek. MemoryContextSource must enforce a strict token budget.
RAG budget example:  max_retrieval_candidates: 40  max_reranked_results: 12  max_memory_context_tokens: configurable  max_single_chunk_tokens: configurable
Prefer fewer high-quality memories to large low-relevance context.
Deduplicate semantically similar chunks.
Do not include superseded or expired memories.
Include memory IDs/provenance in hidden structured metadata, not necessarily in spoken/display output.
ContextBuilder labels retrieved content as untrusted memory/source data.
17. Prompt-Injection Boundary
RETRIEVED MEMORY IS DATAA memory/document may contain text such as “ignore previous instructions” or fake tool commands. ARTHUR must treat all retrieved memory as untrusted content. It cannot modify system policy, permissions, tool schemas, mode, or approval rules.
SYSTEM / POLICY  authoritativeTOOL DEFINITIONS / PERMISSIONS  authoritativeRETRIEVED MEMORY  <memory-data>    ... untrusted text ...  </memory-data>USER MESSAGE  user input
Never concatenate memory text into the system policy section.
Do not parse tool calls out of memory content.
Memory cannot request mode changes.
Tool output stored as memory is also untrusted on later retrieval.
Add adversarial tests containing prompt-injection strings in both Personal and Business stores.

20. Automatic Memory Extraction
After a successful conversation turn, ARTHUR may run a memory-extraction step using the existing DeepSeek ModelGateway. This is not a second agent with unrestricted powers. It is a strict structured extraction task.
MemoryCandidate {  text: string  type: MemoryType  subject_key?: string  project_key?: string  confidence: number  importance: number  reason: string  should_store: boolean}
The extractor must be instructed to avoid storing:
temporary conversational filler
guesses presented as facts
secrets/credentials/tokens/passwords
large copied blocks better represented as documents
information belonging to the opposite mode
model-generated conclusions with no supporting user/tool source unless explicitly marked low-confidence

21. Deduplication
Memory should not grow by storing the same fact after every conversation.
Deduplication order:1. Normalize canonical text.2. Compare exact content_hash.3. Search same subject/type for high semantic similarity.4. If equivalent, update provenance/verification timestamp instead of creating duplicate.5. If contradictory/newer, invoke supersession policy.
22. Supersession and Contradictions
ARTHUR must preserve history without retrieving stale facts as current truth.
old memory: ACTIVEnew verified replacement arrives   |   +--> old.status = SUPERSEDED   +--> new.supersedes_id = old.id   +--> new.status = ACTIVE
Do not physically delete superseded memories during normal updates.
Normal retrieval excludes SUPERSEDED.
If conflict confidence is low, keep both but mark conflict and avoid presenting either as certain.
Explicit user correction has stronger authority than an inferred memory.
Document/tool-source facts carry their source timestamps/provenance.
23. Forget / Delete
DELETE /v1/memory/{memory_id}orPOST /v1/memory/forget
Deletion must target the active domain only. A Personal session cannot delete a Business memory ID even if the caller somehow knows it.
Mark item DELETED and remove it from FTS/vector retrieval immediately.
Delete/clear vector chunks transactionally where practical.
Retain minimal audit tombstone if required for integrity, without retaining deleted sensitive text.
A deleted item must not reappear through stale caches.

32. Secret Safety
Reuse the centralized Phase 1 sanitizer before memory persistence.
Reject or redact credential-like structured fields.
Do not create embeddings for raw secret values that policy removes.
Do not keep unsanitized copies in ingestion staging tables.
Tool results must be sanitized before candidate extraction or storage.
Session/API memory listing must return sanitized display text only.
Deletion/forget must clear secret-bearing content from active retrieval stores.
33. Idempotency / Crash Consistency
Memory writes and document ingestion must follow the hardened Phase 1 idempotency philosophy.
ingestion_request  pending    -> writing    -> completed    -> failedsame request_id + same request_hash:  return/recover same logical resultsame request_id + different hash:  reject
Reserve the request before embeddings/index writes.
Define recovery for crash after DB rows but before vector/FTS indexing.
Use reconciliation on startup or explicit repair function for incomplete indexing states.
Do not allow two concurrent identical ingestions to create duplicate documents.
Delete must be idempotent.
34. Caching
Caching is optional in Phase 2. If added, every cache key must include the trusted memory domain/context key. Never share a retrieval cache between Personal and Business.

Paraphrased query found through embeddings.

Superseded/deleted/expired memories never appear.
Duplicate chunks collapse appropriately.

40. Required Tests — Security
Prompt-injection string inside Personal memory cannot alter tool permissions.
Prompt-injection string inside Business document cannot change mode.

Secret-like tool output is sanitized before memory extraction.

Malformed extraction JSON cannot write memory.

41. Required Tests — Crash / Concurrency
Two concurrent explicit remember calls with same idempotency key create one logical memory.
Two concurrent document ingestions with same key create one logical document.
Crash after memory row write but before vector index can be reconciled.
Crash after vector write but before completion does not duplicate on retry.
Concurrent delete/search never returns a memory after delete is acknowledged.
Concurrent Personal and Business ingestion cannot cross handles/stores.
Both memory DB migrations can start concurrently without corruption.

PHASE 3 GATEProceed only when the audit confirms that Personal and Business memory cannot cross through retrieval, caches, IDs, document ingestion, mode switches, automatic extraction, or failure fallback.
