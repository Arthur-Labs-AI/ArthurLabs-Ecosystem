# The Verification Chamber — visual storyboard and implementation plan

## Composition
A near-black forest-green environment, real eye/S brand, oversized restrained hero, original dashboard capture, and primary download CTA introduce the product. A fine central spine beneath the introduction becomes a tall camera journey. The desktop canvas uses approximately 69% of the film width; a 31% explanation rail follows one stage clock. The mobile canvas switches to a 360-unit vertical world and full-width stacked explanation, not a tiny desktop fan-out.

## Nine shots / continuous timeline (normalized scroll)
1. **Entry (0–.10):** Desktop/CLI origin enters as a revision object. A vertical line grows toward the Linux runtime. Camera follows downward. Explain runtime ownership.
2. **Snapshot (.10–.20):** Revision settles into manifest-bound frozen bytes. Corners close around the snapshot. Scope/configuration become visible. Full/Targeted changes scope only.
3. **Split (.20–.34):** Junction opens, three SVG paths progressively draw while endpoints spread. Persistent packets follow selected curves. Camera pulls back. Unselected lanes remain inactive and never show execution. The defining midpoint is .245, not a faded three-card endpoint.
4. **Workspaces (.34–.47):** Harness chambers expand independently. Each is labeled private/disposable and derives from the same snapshot. Desktop remains spatially parallel; phone expands into readable vertical chambers with a harness focus selector.
5. **Investigation (.47–.60):** Camera approaches the selected chamber. Line highlight follows authored code; a source observation becomes evidence and a finding. Identical investigative responsibilities, no invented reviewer specializations or live response typing.
6. **Partial outcomes (.60–.71):** Chambers compact into independent result surfaces: OpenCode completed; DeepSeek partial output (failed AgentRun with usable evidence); GLM failed before report. Parent outcome derives from selected sample records using inspected aggregation rules. Partial is never “verified complete.”
7. **Convergence (.71–.86):** Three provenance-preserving streams curve toward separate positions in a shared run overview. Evidence/finding packets keep their harness IDs. Paths approaching each other do not mean fusion, agreement scoring or deduplication.
8. **Report (.86–.96):** Stream positions align with an expanding, clipped DOM report surface. The visitor can select each originating harness, inspect its status, source reference, limitation and snapshot identity. JSON/log product capability is described separately from sample data.
9. **Completion (.96–1):** Same report remains available; independent identity and recorded history are emphasized. Native scrolling releases into the supporting sections without a blank tail. Optional Nexus relationship is explained later as conceptual, not a working native return.

## Supporting composition
Editorial harness section → interactive Full/Targeted scope comparison → explicit finding-to-AgentRun-to-snapshot provenance → real-project capabilities and authentic fixture UI → supported CLI reference / separate Nexus relationship → verified individual download center + Suite/source/docs links.

## Architecture review (ten answers)
1. Source of truth: one ScrollTrigger-backed progress clock; pure geometry functions derive every visible position/path/packet. Authored data owns sample findings; verified typed metadata owns downloads.
2. Ownership: client experience owns harness selection, scope, focus and reduced-motion manual stage. None writes an application or provider.
3. Direction: route composes hero, experience/support and downloads. Geometry/data are stable and independent of React. Renderer consumes their outputs; no import back into route.
4. Contracts: typed HarnessId/scene/scope/release records only; no application database handles, credentials, run invocation or live objects cross boundaries.
5. Failure: catalog incomplete/withdrawn metadata fails closed; at least one illustrative harness remains selected. JavaScript-disabled/reduced users can read all nine stages and source boundaries without a scroll trap.
6. Lifecycle: GSAP matchMedia owns the timeline/trigger; effect cleanup reverts both. Configuration changes apply the existing progress, not another clock. Resize refresh preserves progress-to-scene derivation.
7. Tests: pure geometry/outcome/scope/release guards plus actual browser path dash/transform/position and identity measurements. No label-only motion assertions.
8. Compatibility: add only `/sentry/concept`, isolated modules/styles/assets/tests. Existing `/sentry`, Landing, Suite, Nexus and global release catalog remain unchanged. Rollback removes these new files; no migration.
9. Observability: data-ready/progress/stage/selected, path drawing/packet positions, explicit simulated statuses and release-verification receipt. Record continuous desktop/phone browser videos and screenshots.
10. Security: no model calls, application processes or sample-code execution. Installer was streamed for hash verification but never executed. Only pinned, verified HTTPS release metadata enables links. Signed/unsupported-platform claims prohibited.

## File plan
- `src/app/sentry/concept/page.tsx` server composition/metadata.
- `src/components/sentry-concept/{data,geometry,createChamber}.ts` authored explanations, deterministic positions and one animation clock.
- `Hero.tsx`, `ChamberExperience.tsx`, `PipelineScene.tsx`, `Explanation.tsx`, `RunReport.tsx`, `SupportingSections.tsx`, `Downloads.tsx`, `releases.ts` reusable components/contracts.
- `chamber.module.css` scoped responsive visual system.
- `tests/sentry-concept.spec.ts`, isolated capture/record/performance scripts and reports under this artifact directory.

No existing product page or shared styling will be changed. Human creative review is the final acceptance gate.

Rendered refinements: in-film nonmodal harness/scope configuration permits selection changes at the current scroll position; readiness guards prevent pre-hydration chapter clicks; mobile path layers sit behind all private workspace panels; internal footers explicitly reset shared document-footer styles. Half-split nodes emerge early enough to read the harness identities before full expansion.
