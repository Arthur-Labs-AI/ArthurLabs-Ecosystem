# M04.7B Phase 4A: TypeSafe JEV identity provider adapter

Status: implemented and tested offline with a scripted transport; privacy documentation aligned with the accepted opt-in product policy (section 3). NOT activated: nothing in the app constructs the adapter, no command or UI exposes it or its credential or consent, there is no revision synthesis, and no live request has been made. Schema stays v8; M04.7A is unchanged. The Android 16 KB-page APK check remains an open release item (see `m047b-phase2-schema-v8.md` section 9).

## 1. Official API contract (verified 2026-10 against docs.typesafe.ai)
Sources: [Introduction](https://docs.typesafe.ai), [documentation index](https://docs.typesafe.ai/llms.txt), [full docs](https://docs.typesafe.ai/llms-full.txt), [Models](https://docs.typesafe.ai/models), [Legal](https://docs.typesafe.ai/legal).
* `POST https://api.typesafe.ai/v1/systemone`, header `Authorization: Bearer <API_KEY>`.
* Request `{ state, model, questions }`: `state` is a string, object or array (text only); `questions` is a map of named typed questions (`noul`, `choice`, `score`); max 255 options per Choice.
* Response `{ model, answers, usage }`. Noul: `{type:"noul", noul}` (a probability; NO separate confidence). Choice: `{type:"choice", choice, probabilities, confidence}`. `usage` has `input_tokens`, `output_tokens`.
* Errors: `401` missing/invalid key, `422` invalid request, `429` rate limited and `529` overloaded (retry with exponential backoff).
* Models: `jev-1.13.0` is current, also reachable as `jev-latest` and `jev-preview`. Pricing: input tokens only, $0.042 per million, output free. Limits: 64k context, state plus longest question 32k tokens, 80 requests/second and 100k tokens/second ("adjusting dynamically").
* Language: "English is the primary training language and where accuracy is currently best"; other languages are accepted at lower accuracy. Nothing is documented for Bulgarian specifically.
* Not documented (so not relied on): a request-id response header (the Phase 0 harness read `x-typesafe-request-id`; the adapter neither needs nor stores it), the exact `Retry-After` behaviour (honoured if sent, capped), per-account limits.

Mismatch with the Phase 1 classifier contract (handled in `jev::protocol`): JEV returns probabilities per question, not an `IdentityClassifier` signal. The adapter maps them to `CandidateSignal` (section 4). The Phase 1A benchmark harness is research code, not a production client, and its request shape differs from what production sends (below).

## 2. Pinning
`JEV_MODEL = "jev-1.13.0"` is sent in every request and must be echoed exactly in every answer; anything else (including `jev-latest`, a newer version, or a missing model) is `UnexpectedModel`, is never retried, and fails closed. The resolver policy built by `jev::resolver_policy()` accepts only this id. If the pinned model is withdrawn the provider answers with an error and Arthur does NOT substitute another model.

## 3. Privacy: accepted product policy, verified provider documents, open questions
### A. Engineering readiness
The adapter is a disabled, unreachable provider boundary: opt-in is required by construction (consent, Evolution's own switch and a TypeSafe credential must ALL hold, rechecked before each request and inside the commit), nothing is sent otherwise, and no shipped code can turn it on. It does not depend on any contractual retention guarantee.

### B. Explicit informed user authorization (accepted product decision)
TypeSafe JEV MAY process a person's personal Arthur knowledge when that person explicitly opts in after an accurate disclosure. Zero-data-retention guarantees are NOT a prerequisite for voluntary personal use. This approves the intended design only; it does not activate the unfinished pipeline, and it does not authorize sending real captures during development or testing (live checks stay synthetic). The consent contract (section 6) requires: OFF by default; explicit, independently persisted, revocable; never implied by a key or by any other setting; never migrated from an older disclosure. The disclosure a consent screen must show is `jev::DISCLOSURE_POINTS` (pinned to `DISCLOSURE_VERSION = typesafe-optin-2026-10-v1` by a checksum test). In substance: selected snippets (one idea's exact words and up to four same-project ideas) are sent to a third party; TypeSafe states it will not train on input; retention and logging of requests are NOT fully established in its published terms; processing may occur in the United States; turning the feature off stops future requests but does not delete what TypeSafe may already hold; it is off until chosen. The screen itself is Phase 5.

### D. Outstanding questions (transparency and legal; none blocks the adapter)
1. The maximum retention period of request and response contents, and whether full inputs are logged and for how long, remain unestablished; the disclosure says so rather than guessing. A direct written answer from TypeSafe would let the disclosure be made more specific (bump `DISCLOSURE_VERSION`).
2. The subprocessor list must be read in a browser and recorded.
3. Which agreement governs an app developer's API key versus an individual user's data, and whether the DPA/SCCs cover end users' data sent through a developer account, is unclear.
4. A future public or multi-user release needs its own data-protection review (controller/processor roles, lawful basis, user rights and deletion requests, cross-border transfer, children, retention statements, notice to users). An opt-in toggle alone is not assumed to satisfy every obligation.
5. Accuracy on Bulgarian and mixed-language text is documented as lower; it must be benchmarked before any claim of quality.

## 4. Adapter architecture (`src/jev/`)
* `protocol`: builds one request per run and validates the answer. Pure, no I/O. What is sent: the claim title and text, the exact words it came from, and at most four candidate ideas (title and text) under opaque ids `a`..`d`. NOT sent: the rest of the capture, Arthur object or revision ids, project name or id, other projects' ideas (refused outright), timestamps, credentials. User text is only ever data inside `state`; the instructions are fixed text.
* Questions per request (one request per run): `relation` (Choice over `revise_x`, `new`, `uncertain`), `referent` and `supersedes` (Noul), and per candidate `redef_x` (Noul reframing guard), `kind_x` (Choice reframing guard) and `change_x` (Choice: additive, correction, replacement, subtask, other).
* Three runs per claim with the ideas listed, and options ordered, differently (identity, reverse, rotation); answers are keyed by opaque id so the mapping back to candidates cannot drift. Repetition reduces positional noise only and is NOT independent verification.
* Mapping to `CandidateSignal`: `same_proposition` = Choice probability of `revise_x`; `reframing` = max(Noul redef, Choice reframing); `relation` picks the RISKIER reading at a low cut-off (reframing, then subtask, then replacement, then distinct, then correction, else additive); `referent_resolved` and `explicit_supersession` need a HIGH Noul. The resolver (unchanged, provider-independent) then requires unanimity, a unique target, project isolation and its deterministic vetoes. All cut-offs are EXPERIMENTAL and uncalibrated.
* Validation (untrusted answers): model id exact; answers exactly the questions asked; Noul and probabilities finite and in [0,1]; probabilities cover exactly the offered options and sum to 1 (+-0.06); the chosen option is the most probable (+-0.011); a confidence present. Anything else is `Malformed` and never repaired or retried.
* `client`: bounded in-flight requests (semaphore, 2), explicit per-request timeout, bounded retries for transport failures only (timeout, network, 429, 529, 5xx; exponential backoff, `Retry-After` honoured and capped, cancel-aware), a per-capture request budget (24 including retries), a per-day cap, redacted accounting (`Diagnostics`: counts, tokens, estimated cost, failure codes; no text, headers, payloads or ids).
* `transport`: the one POST. rustls, no redirects (the key never follows one), bounded response read (256 KiB). Tests replace it; one test exercises the real transport against a localhost server.
* `consent`: section 6. `provider`: ties it together and implements `AsyncIdentityClassifier`.

## 5. Async to sync, and why it is concurrency-safe
Phase 1 kept `IdentityClassifier` synchronous. Instead of rewriting the resolver: `commit_with_identity` is now `async`; it (1) takes a short snapshot read, (2) awaits `AsyncIdentityClassifier::classify_capture` for ALL claims, handing it only the already-filtered same-project candidates (`identity::eligible_candidates`), (3) wraps the finished results in `Prefetched`, a synchronous `IdentityClassifier` that replays them by claim ordinal and refuses a request for a different candidate set, (4) runs the unchanged pure `resolve_capture`, (5) drafts and commits in ONE short immediate transaction. No `block_on`, no nested runtime, no blocking on a runtime thread, and no SQLite lock during any request (a test edits the store from inside an in-flight request; it would deadlock otherwise). The result is revalidated at commit by the existing compare-and-set on the exact base revision. Enabled state and consent are checked before the request, after the wait (a late result is discarded) and again inside the commit transaction (`evolution_withdrawn` veto).

## 6. Consent and credential
* Consent is its own record (`jev_consent.json`, app-private, atomic write), default OFF, tied to provider `typesafe` and the CURRENT `DISCLOSURE_VERSION` (`typesafe-optin-2026-10-v1`; the earlier `typesafe-2026-04-v1` grant, if any ever existed, no longer counts and is never migrated; constructing the consent or reading an old record writes nothing); a missing, damaged, foreign-provider or older-disclosure file means NOT consented. Revoke is durable-first and immediate; it never touches the OpenAI key, Semantic Recall, Automatic Connections or Evolution's own switch (tests). A key alone is never consent.
* Credential: a dedicated native-only slot `ProviderId::TypeSafe` in the existing `SecretStore` (Android Keystore bridge, 0600 file on desktop). It is deliberately NOT in `ProviderId::ALL`, `ProviderId::parse` never yields it, and it serves no capability, so the AI & Voice commands cannot set, read, delete or test it and it is never exposed to React; another provider's key is never used. No key is hardcoded or written to logs, the database audit or benchmark output.
* The key shared earlier in conversation is COMPROMISED: it was not read or reused here and any live acceptance needs a rotated key.

## 7. Reliability and failure mapping
Typed `JevError` prints only a fixed code. Pre-request refusals (disabled, no consent, no credential, cross-project, too many candidates, input over 12k characters, cancelled, budget) send nothing. A failure that will repeat (auth, exhausted retries, rate limit, overload, budget, cancel, withdrawn permission) stops the rest of the capture instead of hammering the provider. The pipeline records every failure as `classifier_failed` and keeps the claim as an UNCHECKED object (never a verified NEW); the precise code lives only in `Diagnostics`.

## 8. Production activation safeguards
Unchanged and tested: the injector is test-only; no shipped file mentions the adapter, consent or transport (`jev::architecture_tests`); the adapter imports no storage, graph, Recall or command code; Evolution's own switch defaults OFF with no UI control; real captures cannot reach JEV through Arthur. Before a user can opt in, ALL of: the Phase 5 consent screen showing `DISCLOSURE_POINTS` and writing the consent record only on an explicit choice, a native credential command, real revision synthesis plus the veto-only verifier (Phase 4B), re-benchmarking THIS request shape on human-adjudicated data (including Bulgarian and mixed text), the review UI, and the Android 16 KB check. The questions in section 3D do not block personal opt-in use but must be answered before a public release.

## 10. Proposed Phase 4B contract
Phase 4B adds the revision drafter (real synthesis, deterministic validation: lengths, kind, coverage of the claim's words, no new numbers or names, correction drops the old value) and an INDEPENDENT veto-only verifier (a different model family; it can only turn REVISE into UNCERTAIN). Interface: it implements the existing `RevisionDrafter` and adds a `RevisionVerifier` called inside `plan_one` after the draft and before commit; both are fed only the claim, its exact words and the target text, under the same consent. The pipeline contract, the commit transaction and the resolver stay as they are.
