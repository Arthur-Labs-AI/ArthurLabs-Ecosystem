# M04.7B Phase 2: schema v8, durable identity persistence

Status: implemented, STORAGE ONLY. Nothing in the running app writes these tables: distillation, commands, Graph Integration (M04.7A), the UI and every provider are unchanged. The Phase 1 report (`m047b-phase1-identity-core.md`) is kept as written; this document supersedes its sketches of v8 where they differ (listed in section 1).

## 1. Where the Phase 0/1 proposal and the real code differed
| Proposal | Reality | Decision |
|---|---|---|
| `pending_claims.project_id` | A capture's project is movable and authoritative; a stored copy goes stale on a move. | No column. A claim's project is its capture's CURRENT project (join), so a moved capture takes its claims with it. |
| `identity_decisions` as a per-object record | `distillation_runs` is one row per capture, `object_sources` has one span per object, there is no per-claim table. | Keyed `(capture_id, ordinal)`, FK to `distillation_runs(capture_id)`: a decision cannot exist for a capture that was never distilled. |
| Claim ordinal aligned with the created object | Uncertain claims create no object, so object order and claim ordinal cannot be tied in SQL. | Not enforced; the decision links the object by id (`created_object_id`) and the schema checks it originates from that capture. |
| Pending "quota" | A DB quota would force a drop or refusal. | None in storage. A full queue is a Phase 3 routing decision (overflow becomes a separate object, `unchecked_reason = 'review_quota'`); storage can never discard. |
| `distillation` origin for automatic revisions | Declared but unused; its span semantics mean "interpreted from this capture". | Automatic revisions use origin `system` (already in the CHECK): no `thought_revisions` rebuild. |
| Expiry marks a claim resolved | A claim is not resolved until the authoritative operation happened. | `due_at` is only reported (`due_pending_claims`). `separated` with method `expiry` exists for the Phase 3 sweep, and still creates a real object. |
| User-accept "origin" | Accepted revisions are Arthur-written text confirmed by the person. | origin `system`; `pending_claims.resolved_method = 'user'` records the confirmation. |

## 2. Schema v8 (`SCHEMA_V8` in `storage/migrations.rs`; plain `CREATE`, additive, no backfill)
**identity_decisions** `PRIMARY KEY (capture_id, ordinal)`: `outcome ∈ new|revise|uncertain|unchecked`, `unchecked_reason`, `target_object_id`, `base_revision_id`, `result_revision_id`, `created_object_id`, `policy_version`, `model_id`, `decided_by ∈ gate|fallback`, `vetoes_json` (array, ≤1 KB), `audit_json` (object, ≤4 KB), `decided_at`. A shape `CHECK` makes the outcomes distinct: `new`/`revise`/`uncertain` REQUIRE a model id; `unchecked` requires a reason, is `fallback`, and cannot be dressed as `new`. Triggers: immutable, never deleted; `revise` needs a committed `system` child of the stated base on the stated object that carries evidence from the same capture; `new`/`unchecked` need an object whose `object_sources` capture matches. Indexes on target and created object.

**revision_evidence** `PRIMARY KEY (revision_id, ordinal)`, `UNIQUE (revision_id, capture_id, source_start, source_end)`: `object_id`, `capture_id`, span, `role ∈ asserts|corrects|replaces`, optional `(retracts_revision_id, retracts_ordinal)` FK to an earlier evidence row (both or none; only for `corrects`/`replaces`), `interpretation_label` (≤200, interpretation, never source text), `created_at`. Triggers: immutable, never deleted; only for a `system` revision; `object_id` equals the revision's object; span inside the capture (`length()` counts characters, matching code points); no new evidence once the revision has descendants; a retraction target must be evidence of a strict ancestor revision. Indexes on object and capture.

**pending_claims** `seq`, `id`, `UNIQUE (capture_id, ordinal)` with FK to `identity_decisions(capture_id, ordinal)`: claim fields (`kind`, `title`, `body`, span), `candidate_ids_json` (1–4), `reasons_json`, `reframing`, `state ∈ open|deferred|accepted|separated`, `due_at`, `created_at`, `updated_at`, `deferred_at`, `resolved_at`, `resolved_method ∈ user|expiry`, `resolved_object_id`, `resolved_revision_id`. State-shape `CHECK`: open/deferred carry no resolution; accepted needs object, revision and method `user`; separated needs an object and no revision. Triggers: never deleted; insert only as `open`, only for an `uncertain` decision, span inside the capture, candidates must be existing objects of the capture's project; claim content immutable; terminal states final; allowed transitions only `open→deferred|accepted|separated`, `deferred→open|accepted|separated`; `accepted` requires a committed `system` revision of a candidate carrying THIS claim's span as evidence; `separated` requires an object created from THIS claim's span.

## 3. Evidence invariants
* Evidence is verbatim capture spans. A synthesized revision has NULL span columns of its own; it is identified by `origin = 'system'`.
* **Historical** = every span in the revision's ancestry (origin spans and evidence rows), whatever happened to it. **Active** = spans legitimately supporting THIS revision. **Withdrawn** = spans a later revision's `corrects`/`replaces` row names as withdrawn.
* Derivation (`evidence_store::evidence_support`, read time, nothing cached): walk back through `system` revisions to the first non-automatic one. An `initial` base contributes its origin span as active; a `user_edit`/`merge` base contributes nothing (the person's words are not claimed to rest on a capture) and the attribution is `Unknown`. Replaying forward: `asserts` adds; a correction/replacement with named targets withdraws exactly those; WITHOUT named targets all earlier active evidence becomes historical (`inherited_demoted = true`); a revision with no evidence demotes everything and is `Unknown`.
* Attribution is only ever `OriginSpan`, `ContributingSpans` (these spans contributed; WHICH sentence rests on which span is deliberately not recorded or reported) or `Unknown`. No claim-level attribution is invented.
* "Never infer all historical evidence supports the current revision": `historical` is a separate list and is never promoted into `active`.

## 4. Pending-claim state machine
`open ⇄ deferred`; `open|deferred → accepted` (needs the committed revision + evidence + candidate target + method `user`); `open|deferred → separated` (needs the created object; method `user` or `expiry`). Terminal states never change. Repeating the SAME resolution returns the stored one without writing (`applied = false`); the opposite resolution is a `Conflict`. `accept_pending_claim` and `separate_pending_claim` do the authoritative operation and the state change in ONE immediate transaction, so a terminal state cannot be recorded without it, and the schema re-checks the proof. Accept also refuses (writing nothing) when the target is not a candidate, the capture and target are no longer in the same project, the project is archived, or the expected base is no longer current (stale: a user edit wins). Separate refuses in an archived project and creates the object in the capture's current project.

## 5. Transaction boundaries and idempotency
`CaptureStore::in_identity_transaction(|tx| …)` runs `*_in(&Connection)` functions in one IMMEDIATE transaction; it commits only on `Ok`. The future pipeline composes: distillation run → `revise_if_current_in` → `attach_revision_evidence_in` → `record_identity_decision_in` / `stage_uncertain_claim_in` → commit (then the Graph event). A test composes exactly that and shows an interruption undoes every part. Idempotency: a decision per `(capture, ordinal)` (identical repeat = no-op, different = conflict); staging per `(capture, ordinal)`; evidence per span; resolution as above. Audit JSON is built from typed fields (ids, 0–1 scores, counts, allow-listed veto names), never free text; the schema re-checks JSON shape and size.

## 6. Migration guarantees
v7 → v8 is one transaction with the version bump. Tests: fresh v8; a populated v7 database (authoritative-row fingerprint, FTS row count, relations and ownership, projections, projects) byte-identical afterwards, new tables empty, integrity and foreign-key checks clean, old triggers still firing, lexical index consistent, reopen ×3; failure injected at the first, middle and LAST statement leaves v7 exactly as it was (only the blocker survives); a half-run step abandoned without commit is invisible and the next open completes it; a binary at the previous version refuses a v8 file without changing a byte; a database one version AHEAD of the current build is refused untouched.

## 7. Compatibility
Old binaries refuse v8 (existing behaviour). New code on a v7 file migrates on open. Nothing reads these tables yet, so downgrade-by-restore of a pre-migration copy loses nothing. Recall, Graph Integration and every command are unchanged.

## 9. Phase 3 requirements that must not be weakened
* **Atomic disposition.** Every identity disposition and its resulting authoritative action commit in ONE transaction: the distillation run, the object or revision it produced, its evidence, the `identity_decisions` row and any `pending_claims` row. Use `in_identity_transaction`; never several independent commits.
* **`unchecked` is not a verified `new`.** `unchecked` means identity was not established (disabled, invalid input, classifier failure, malformed signals, review quota). It must stay a separate outcome in storage, metrics, UI and any benchmark; only `new` (a classifier ran and found no plausible referent) counts as an identity decision.
* **No fabricated spans.** A synthetic (`system`) revision never carries a direct capture span of its own. Its support is `revision_evidence` rows: verbatim spans that contributed, with no sentence-level or claim-level attribution beyond what the data proves.
* **Evidence stays separated.** Historical and withdrawn evidence must never be shown as current supporting evidence; only `evidence_support(...).active` may be presented as support, and `Attribution::Unknown` must be shown as unknown.
* **Pending claims never disappear.** Neither a full review queue nor expiry may delete, hide or drop a claim. A full queue routes the incoming claim to a separate object (`unchecked_reason = 'review_quota'`); expiry creates a separate object via `separate_pending_claim(.., "expiry")`. Rows are never deleted and a claim is never marked resolved without its authoritative operation.
